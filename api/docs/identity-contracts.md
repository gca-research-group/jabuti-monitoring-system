# Identity HTTP contracts

Identity requests and responses now live under `identity.adapters.http.dto`.
Routes and login response fields (`id`, `name`, `email`, `accessToken`) are unchanged.
API-key creation still returns `userId` and `keyHash`; the Java response property
is `apiKey`. This is the newly generated raw key, returned only by creation. The
stored SHA-256 secret hash is never included in HTTP responses.

Compatibility changes for identity endpoints:

- User responses, including lists, omit `password` entirely.
- User creation requires a nonblank name, a valid nonblank email, and a nonempty
  password. Login requires email and password. Password text is never trimmed;
  creation and replacement use the configured password encoder.
- New users default to enabled. A supplied `status` must be non-null.
- Existing PUT `/user/{id}` now changes only supplied fields. Omission preserves
  stored values. Explicit null clears photo and remarks; null or empty password,
  null/blank name or email, and null status are rejected. Photo is any optional
  string up to 255 characters, with no URL validation.
- User, login, and API-key creation requests reject unknown fields, including
  record IDs and response-only fields. Create IDs are generated by persistence;
  the URL alone identifies an update. API-key requests accept only required userId.
- Identity validation errors retain the `message` shape, identify invalid fields,
  and exclude rejected values and credentials. Other endpoints retain their
  current request and error policies.

The user form sends only dirty fields on update, retains nulls, and omits an
untouched password. Login state and management models are separate. Existing
legacy DTO classes remain available for the later cleanup ticket; identity
operations no longer consume them. No database migration or runtime-profile
change is required, and no password-strength or email normalization/uniqueness
policy is added.

During this CRUD transition, identity application services and the user store
reuse the role-specific contracts in the agreed `identity.adapters.http.dto`
package as their public input/output types. This is an explicit exception to the
HTTP dependency direction described in ADR 0001: HTTP and application layers
share these data contracts, while servlet, cookie, and response handling remain
in adapters. Introducing duplicate application records solely to translate the
same fields is deferred; the ticket's approved placement and existing CRUD seam
are retained.

The photo editor accepts a short string rather than embedding an uploaded image
as a base64 data URL. Clearing the input sends null. An unchanged legacy photo
longer than 255 characters remains untouched when another field is edited; a
new or changed photo must satisfy the current limit.
